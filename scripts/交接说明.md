## 数据模型（GitHub 仓库根目录的 JSON 文件）

- `photos/` 目录：照片图片文件（上传后自动写入）
- `messages.json`：留言板 `{ id, name, content, time }`
- `plans.json`：周计划 `{ id, content, submitter, startTime, deadline(提交后7天或用户指定), score(null|0-100), scoredBy, scoredAt }`
- `comments.json`：照片评论 `{ id, photoId, content, author, time }`
- 通用读取函数 `fetchGithubJson(relPath)`：渠道顺序 raw.githubusercontent → jsDelivr CDN → Pages 静态 → GitHub API

## 重要技术约束与历史坑（务必遵守）

1. **照片上传 base64**：图片 dataUrl 去掉前缀后的 base64 直接作为 GitHub API 的 content 字段（ghPutFile 的 `alreadyBase64=true`），严禁再用 `btoaUnicode` 二次编码——曾因双重编码导致线上照片全损坏（文件变成 ASCII 文本），修复方式是把文件 base64 解码一层还原
2. **展览页读取**：浏览器有 token 时走认证 API（实时），无 token 走匿名多渠道；图片 URL 用 Pages 静态优先（raw 在这台机器经常超时）
3. **Token 存 localStorage**，清浏览器缓存会丢；强刷用 `Ctrl+Shift+R`，不要引导用户"清除浏览器数据"
4. **留言板匿名实时依赖 Cloudflare Worker**：https://our-moments.zengyangyu.workers.dev（POST /messages，token 在服务端 env.GITHUB_TOKEN，worker 代码在 `scripts/guestbook-worker.js`）
5. **通用工具函数**（fmtDateOnly、fmtCountdown、authorColor、esc 等）在 `assets/js/common.js`（全局），不要只在页面局部定义——曾因 fmtDateOnly 只在展览页定义导致管理页周计划崩溃
6. **部署脚本 `scripts/deploy.sh`** 会跳过 `photos.json`/`messages.json`/`photos/`（保护线上用户数据不覆盖），勿移除该保护
7. 本机 bash 里 python 可能解析为 LibreOffice 的 python（功能兼容但路径不同）；大文件上传用临时文件传递 base64（避免命令行参数超长）

## 上线流程（每次改完必做）

1. 修改本地文件
2. `node --check` 校验 JS 语法（如 `node --check assets/js/admin.js`）
3. 用 GitHub Contents API 上传：GET `/repos/yuzengyang/moment/contents/<path>` 拿 sha → PUT（content 为文件 base64、branch:main、带 sha）。bash 循环 + 临时文件传递
4. Pages 自动重建约 1-2 分钟，构建状态查 GET `/repos/yuzengyang/moment/pages/builds/latest`
5. 改动涉及渲染逻辑时，务必做运行时验证（node mock 测数据层）——曾因变量声明顺序 TDZ 导致页面渲染崩溃

## 数据层测试方法
